去年帮区里做过一轮社区服务站选址，当时靠表格加手工试，事后被人指出白白多建了一座。这回我想把这件事做成一个正经的后端，给规划科几位同事轮流用。

问题本身不复杂：平面上散着一批居民点，另有一批可选的站址，所有站共用一个服务半径，一座站照顾得到的是和它直线距离不超过半径的居民点。要找的是站数最少的开站组合，让每个居民点都至少被一座开了的站照顾到；同事可以点名几座"非建不可"的站，求解时必须把它们算进去。这里的"最少"要求精确最优，结果里得写明是否已证明最优，没证明的一律不许标成最优。距离取平面欧氏距离，坐标单位固定。所有候选址全开也还有人够不着时，返回无解并列出够不着的那些点，不能报成功。半径非正、居民点为空、候选址为空、点名的站编号不存在，都要返回指向具体字段的错误。

方案得能存下来。同事围绕一个选址项目反复调整，每改动一次居民点或候选址就生成新版本，旧版本连同当时算出的方案原样保留，可以按版本号取回对比；同一版本重复发起求解，不应产生重复记录。

规模上去以后，一次求解可能要几十秒甚至更久，所以求解要做成后台作业：提交后立刻拿到作业编号，能查进度（已探索的规模、当前最好站数、已证明的下界），能主动取消，也能设时限。时限到了或被取消时，作业交出手上最好的可行方案、下界和两者之间的最优间隙，状态写明是超时还是取消，而不是完成。多个作业同时跑互不干扰；服务重启后已完成作业的结果还在，没跑完的标成中断，别一直挂着"运行中"。

还有个高频操作：在某个已有版本上增删几个居民点再求一次。我希望这一步能借上一版的结果少算点，但怎么借由你决定——在旧最优解上修补后再证明最优、只复用覆盖关系后从头重解，或者别的思路都行。请在文档里讲清你选了哪种、理由是什么、什么情况下会退回全量重解。无论哪种做法，硬性要求只有一条：增量得出的站数必须与对同一数据从头求解的结果一致，且方案本身满足全覆盖；我会拿随机增删序列反复对拍。

打算写进测试的几条关系：只调大半径，最优站数不会变多；强制开一座原本不在最优解里的站，站数不会少于原最优；拿掉一座所有最优解都离不开的站，站数上升或者变成无解并列出漏点；同一居民点坐标重复出现，站数不受影响；超时作业报的下界不大于真实最优，报的当前最好不小于真实最优。最想防住的三种错：贪心凑出的结果被标成最优、有点漏覆盖却报成功、增量结果和全量对不上。请准备一个诊所选址的小例子，十几个居民点配几座候选诊所，最少站数能手工验算，拿来当回归基准。

接口大致包括：创建选址项目与提交新版本、按版本号取回、在某版本上发起求解作业、查作业进度与结果、取消作业，以及在固定必开约束下给一串半径扫出站数阶梯（扫描同样走作业）。后端语言定 Python 3.12，Web 框架选 FastAPI，持久化用 SQLite 这类轻量存储就够。覆盖关系构建、精确求解、作业调度与取消、版本存储、增量重解和 HTTP 层请分成各自的模块，别堆进一个大文件。镜像请从 python:3.12-slim 起步，打好的镜像跑一个容器就能提供全部接口，数据目录支持挂载，仓库里带上自动化测试。对外只需要 HTTP 接口，不需要页面。
